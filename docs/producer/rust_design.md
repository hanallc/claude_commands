# Rust design rules for producers

Correctness comes first. Then apply “Simple, Fast, Beautiful” in that order. Ask the style unit about hard design calls.

## Modules and crates

- Put each behavior in “the crate that owns the types, data and rules the behavior reads and changes.” Have dependent crates call that crate’s operation. Move behavior to a lower crate only when it owns that behavior. Remove copies from dependent crates in the same change. (behavior-lives-in-its-most-cohesive-crate.md)
- Move a type to the module with its sole constructor, single consumer, or primary mutator before deciding whether to split. Keep a type in place if it forms the public API or has no single owner. Use `support/` only for free functions or traits with no anchor type or behavioral home. They must serve at least two unrelated siblings. Use the nearest common ancestor for callers under different parents. (types-live-with-their-behavior.md)
- Split a flat file only when at least two conditions apply. It defines at least three top-level types absent from each other’s field lists. It mixes domains. It exceeds about 500 lines of non-test code. Distinct sections would benefit from focused tests. Keep a facade only when it serves a purpose. Never keep the original file as a shell that declares the new modules via `#[path]`. Collapse a split when one child has meaningful content, one domain fits below about 500 lines, or all children are thin data files. (when-to-split-a-module.md)
- Draw boundaries around a primary type, its field types, its implementations, and functions that construct or operate on it. Group peer types of equal weight by domain. If two proposed submodules depend on each other, merge them or move the shared type to their parent. (split-by-type-ownership.md, name-submodules-after-anchor-types.md)
- Use `module/mod.rs` for a module with submodules. Use `mod.rs` and `lib.rs` to declare submodules and re-export the API. The module’s anchor type, its field types, and its variant payload types may live at the root with their implementations. Give a supporting type with a long implementation its own module. Put independently constructed supporting types in leaf files, even when they share the root type’s domain. Allow thin delegation in `mod.rs` when it avoids `pub(in crate::...)` for child items. Keep Bevy app and plugin wiring at the root. (module-roots-as-table-of-contents.md, module-structure.md)
- Put unit tests in the file of the primary type whose behavior they assert. Return an owning fixture from a test helper that starts work that can outlive the test. (tests-live-with-the-type-under-test.md, test-fixture-ownership.md)
- In Bevy, keep the plugin struct and its `impl Plugin` in the same module root. Define a plugin when a module needs app registration. A directory feature module’s plugin registers small contributions from children directly. Give a child its own plugin if it needs `&mut App` for registration. Use `pub(crate)` for top-level plugins, `pub` for library re-exports, and `pub(super)` for child plugins. (bevy-plugin-ownership.md)
- Pin dependency versions in the workspace `Cargo.toml` and inherit them in members with `workspace = true`. Set baseline features in the workspace; members add only the features they use. (workspace-dependencies.md)

## Public API

- “A crate exposes what its callers need as named operations with ergonomic signatures.” Accept the caller’s types and return a result the caller can use directly. Have the crate apply its own rules. Provide one public way to perform each operation. Every public operation needs a caller. (crate-apis-expose-behavior.md)
- Use “the narrowest visibility that compiles.” Keep modules private and re-export the intended API. Use `pub` for declarations on the public re-export chain or in a reachable public signature. Use `pub(crate)` for crate-wide access, including non-private internal items in top-level private modules. Use `pub(super)` for access within the parent. Use `pub(in crate::path)` only when a parent’s `pub(super) use` facade needs it. (use-narrowest-visibility.md, use-pubcrate-in-top-level-private-modules.md)
- Get the user’s approval for a new or changed public API. Preserve the existing public API during style fixes, cleanup, and refactors unless the user requests or approves a breaking change. Prefer private wrappers or facade delegation when a refactor needs to preserve an existing public entry point. Include exports, trait implementations, constructors, builders, plugin call forms, and supported examples in that check. (crate-apis-expose-behavior.md, public-api-changes-require-explicit-approval.md)
- Exceptions that nate approved. The producer of the item approves each one and reports it to nate in one line:
  1. A new variant of a public error enum that exists already (nate, 2026-11-19).
  2. A rename of a public error type to the name form of this page (nate, 2026-11-19).
  Each other public API change still needs nate's approval.
- For borrowed parameters, use `&Path`, `&str`, `&[T]`, and `&T` for data from `PathBuf`, `String`, `Vec<T>`, and `Box<T>`, respectively. (borrow-the-slice-not-the-container.md)
- In a library crate, for public failures, return `Result<T, E>` with a public error enum. “Each variant names one failure and carries the value that identifies it.” End the enum name in `Error`, never `Failure`, and name it after the type or operation that fails (`UnfoldError`, `FontLookupError`). Add a word between only to tell apart two error enums of one type; an error enum in the app crate takes the same name form. Derive `thiserror::Error`. Wrap a lower-level error with `#[from]` or `#[source]` so the cause chain survives. Export the error beside the type whose functions return it. Never carry a failure as a `String` field. Never turn a `Result` into an `Option` with `.ok()` at a public boundary. Keep `Option` for ordinary absence, such as a lookup that asks whether a key exists. A lookup for a key that should exist returns `Result`. Keep the return type of a trait signature you do not own. (public-failures-return-named-errors.md)
- In the app crate, use `anyhow::Result` to carry crate failures up to the report. At each level, add `.context(...)` or `.with_context(...)` that names the operation that failed. A fallible Bevy system returns `bevy::ecs::error::Result`, and `?` converts the `anyhow::Error`. Call `App::set_error_handler` once (Bevy 0.20.1). In that handler, resume a panic payload first, because a system panic also reaches it; then log each other error with `{:?}`, so the report keeps the cause chain. A system that returns an error is then logged and the app continues; only a real panic stops the app. Never end the chain with `.ok()` or a log line that prints only the outer message. (app-errors-carry-context-with-anyhow.md)
- Use `bevy_kana` in Bevy crates that can use its API. Keep its newtypes internal. Use `Position`, `Displacement` and `Velocity` for internal fields and parameters where their meanings matter; keep `Vec3` for scale, direction vectors, AABB extents and math locals. Enable the `bevy_kana` input feature only in binaries. Use standard types for public spatial fields and returns, such as `Vec3`. Accept `impl Into<Vec3>` for public spatial arguments. Keep a public `const fn` that a const expression uses. Take `Vec3` directly in that case. (use-bevy_kana-in-all-bevy-crates.md)

## Generics and traits

- “Extract a trait only when two or more types implement it.” A deliberate extension point for downstream crates is the exception. Document that intent on the trait. (dont-create-traits-for-single-implementations.md)
- Implement `From` for a single-input, infallible, lossless, unambiguous conversion. Use `TryFrom` for fallible conversions. Use named constructors for ambiguous interpretations, external context, or required const construction. Retain methods required by traits. (prefer-from-impl-over-named-constructors.md)
- Keep one mechanism for shared behavior. Supply the differences between kinds as data or through one trait method. “A branch for one kind in a shared path is a design change, and it needs the user’s approval.” (one-mechanism-per-behavior.md)
- “Each behavior has one implementation.” Reuse or extend existing logic. Combine near-copies that differ only in data into one function over that data. Combine types when both their fields and their meaning match. (no-duplicate-implementations.md)

## Types

- “Make invalid states unrepresentable.” Put fields that are valid only together in the same enum variant. Enforce value limits with a private field and one checked constructor. Give a state its own type when only that state permits an operation; see the next point. (make-invalid-states-unrepresentable.md)
- Use the typestate pattern when an operation is valid only in some states of a value and the code knows the state at compile time. Give each state its own type. Make each transition a method that consumes the value and returns the type of the next state. A call in the wrong state then does not compile. Use an enum when the state comes from data at run time. (typestate-for-compile-time-states.md)
- Use enums for owned Boolean state in fields, arguments, return values, and local accumulators. Keep `bool` for a required wire field that always carries one value. Apply the rule to the typed result of parsing. Allow `bool` in file-private structs used only for deserialization. (enums-over-bool-for-owned-booleans.md)
- Use an enum with named states when `None` carries a domain meaning, such as `Inherit`. “Keep `Option` when `None` means "absent" and nothing more.” (enums-over-option-when-none-has-meaning.md)
- Introduce an enum when code branches on the same condition in multiple places or an `if`/`else` chain exceeds two arms. Use `match` to enforce exhaustiveness. When the new state comes from one input, implement `From` if the conversion cannot fail and `TryFrom` if it can. Keep a named classifier for multi-input, contextual, or `const` construction. (if-else-chains-signal-missing-types.md)
- In Bevy, default to events with observers. Use messages only for a clear batch or schedule requirement. Emit each change once where the code decides it, and only for entities whose state changed. Keep `Changed<T>` for inspector edits or writes from another schedule. Poll `Added<T>` after a deferred producer supplies a dependency the reaction needs. Make both directions of a state change events (off and on, dim and undim), each started by its own observer. (prefer-events-over-messages.md, prefer-observers-over-polling.md)
- Give a Bevy `SystemParam` bundle the behavior that uses its fields. Its callers should get a resolved result from that behavior. Look for a helper that borrows at least two parameters besides `Commands`. Look for systems that use the same parameters in the same sequence of calls. A system with more than about eight parameters is also a candidate when some parameters serve one concept. Give the bundle its own module once callers span files. (system-params-carry-their-behavior.md)
- A function does not take `&mut World` or `&World` when a narrower Bevy form does the job: an event with an observer, a `SystemParam` with methods, or an entity event or `EntityCommands`. Keep `World` only where Bevy gives nothing narrower, and state that reason in the doc comment. (world-arguments-need-a-reason.md)
